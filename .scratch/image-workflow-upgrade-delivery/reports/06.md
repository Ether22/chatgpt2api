## 素材 API 与07交接

新服务 `services/image_import_service.py`、新路由 `api/image_imports.py`；`api/app.py` 仅注册路由。默认当前元数据保存于本服务 `data/image_imports/<登录身份ID的SHA256>.json`，登录密钥不作为归属键或文件名。

| HTTP | 请求 / 行为 |
| --- | --- |
| `GET /api/image-imports` | 当前身份的唯一素材集合；不读取生图会话详情，不依赖全量历史GET。 |
| `PUT /api/image-imports/md` | multipart `file,request_id,version`，直接替换当前MD，参考图不变。 |
| `POST /api/image-imports/references` | JSON `{request_id,version,name,size}` 先登记文件名与上传意图；严格同名拒绝。 |
| `PUT /api/image-imports/references/{upload_id}` | multipart `file`；`upload_id` 就是登记时的request_id。只完成已登记文件的传输；检查文件名、大小及首次传输摘要。 |
| `DELETE /api/image-imports/references/{upload_id}` | JSON `{request_id,version}`；版本化移除。upload_id尚未到达服务端也可取消，不能只取消客户端Promise。 |
| `DELETE /api/image-imports` | JSON `{request_id,version,upload_ids?:string[]}`；upload_ids应包含客户端已选择但可能尚未登记的在途标识。服务端同时覆盖所有已登记当前参考。 |

成功响应统一为：

```text
{
  version, revision, updated_at,
  md: {name, content, size} | null,
  references: [{request_id, name, size, reference: {id,name,type,url,size} | null, error?}],
  pending: {request_id,version,upload_ids,clear} | null
}
```

- `version` 在 MD替换、参考登记、开始移除/清空时增加；文件传输完成不增加它。`revision` 在每次持久状态保存时增加，客户端只接受不旧于现有revision的响应，避免乱序响应退回就绪状态。
- 替换/移除/清空要求当前version。非同名新增允许旧version，只要不早于最近一次清空；移除只使目标upload_id失效，不阻止其他名字的无冲突新增。清空后的旧登记不得把旧素材重新带回。
- request_id固定标识一个操作，重试须保持原请求体；已完成请求返回当下集合，不重放旧MD或清除后续新素材。receipt只保存请求摘要/标识，不保存多套MD内容或物理素材历史。
- 409表示版本/同名/请求身份冲突，刷新后由用户重新决定操作；507表示保存或清理真实失败，同一操作可重试。清理未完成时 `pending` 保留，跨浏览器可按其原请求重试；目标参考的 `reference` 置空并带错误，不呈现假可用文件。
- **07读取 `md.content`、`references[].name`、已就绪的 `references[].reference`。** 上传中的reference为null，不能当作已准备好；pending清理不是成功状态。08提交仅使用已就绪reference.id，并继续让04/05保存独立轮次快照。
- 前端扩展入口：`web/src/app/image/components/image-import-dialog.tsx`。类型/API：`web/src/store/image-imports.ts`。所有新素材API函数第一参数是已验证会话的 `authKey`，必须保留显式身份绑定，不能退回执行时读取任意当前登录密钥。

## 持久化、并发与引用边界

素材服务只调用04公开 `upload_reference(..., scope="imports")` 与 `cancel_reference_upload(..., scope="imports")`；文件、输入scope、turn_ids、取消墓碑和最后引用物理删除仍完全由04管理。本服务没有复制物理文件生命周期或直接读写其账本。

上传先原子保存登记/摘要，再调用引用上传，最后重新读取当前状态并确认登记仍有效才发布reference。清理先原子保存版本与intent，调用现有取消接口，成功后一次完成元数据；任何阶段失败都留下可GET辨认、可重试的状态。即使物理清理完成而最终元数据写失败，重试仍使用原取消墓碑，并且GET不会把已删参考展示为ready。

**文件上传与取消I/O位于 imports 元数据锁外。** 主审发现初版持锁上传后，新增真实HTTP慢磁盘测试先因GET超过750ms失败；修正后阻塞上传期间GET可读已就绪参考，另一MD操作及时完成、清理intent可见，放行后的迟到上传返回冲突且最终无imports残留。没有改变04引用内部锁；05后续改造仍只需保持其公共契约。

前端素材结构操作按顺序执行，实际文件传输最多4个并行，限制的是浏览器文件传输而非生成/账号槽位。每个request_id重复上传与取消有服务端墓碑保护；旧传输返回不能重新加入已清空集合。新请求绑定发起时的身份，发送前检查当前存储key；身份变化会停止未开始队列、撤销Blob并清除本页素材展示，已提交到服务器的原身份操作按原身份完成。旧请求401不会退出新登录身份。
